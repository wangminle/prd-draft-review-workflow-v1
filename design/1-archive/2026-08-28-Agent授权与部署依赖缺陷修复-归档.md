## 1. 问题背景

本轮修复针对五类相互关联的问题：

1. workspace 类型 Agent 授权缺少创建时的成员和状态校验，存在横向越权风险；
2. 已创建授权在用户被移出 workspace 或 workspace 归档后，可能继续被 RAG 使用；
3. 个人 Agent 弹窗在关键配置加载失败时可能把失败误认为空数据，保存后覆盖原配置；
4. 前端无法明确提交空字符串以清空 System Policy，并可能丢失当前 UI 未展示的工具项；
5. 根依赖缺少 DOCX 嵌入 Excel 转换所需的 `openpyxl`，且 `package.json` 与 `package-lock.json` 的 Node engines 元数据需要保持一致。

## 2. 最终设计决策

### 2.1 Workspace 授权纵深校验

- 创建 workspace 类型授权前，后端必须确认目标 workspace 存在且状态为 `active`；
- 当前用户必须是该 workspace 的 active 成员；
- RAG 实际执行时再次检查 workspace 状态和当前成员关系；
- 授权创建成功不代表永久有效，成员移除或 workspace 归档后旧授权立即失去使用资格；
- 安全边界由后端执行，不依赖前端列表过滤。

### 2.2 个人 Agent 配置防误覆盖

- Profile、授权列表和 workspace 列表属于关键配置数据；任一加载失败时弹窗进入错误态并禁止保存；
- 运行记录和审批列表属于辅助数据，可单独显示加载失败，不阻断基本配置编辑；
- 保存工具白名单时，保留后端已有但当前 UI 未展示的工具，只修改 UI 管理范围内的工具项；
- 加载失败不能伪装为“暂无数据”。

### 2.3 System Policy 清空语义

- 空字符串 `""` 表示用户明确清空 System Policy；
- `null` 或字段未提供均表示不修改；后端只在 `req.system_policy is not None` 时更新，因此显式 `null` 与字段缺省都执行 no-op；
- 前端提交输入框原始字符串，空输入不会被转换为 `null` 或省略。

### 2.4 依赖和锁文件

- 根 `requirements.txt` 包含 `openpyxl>=3.1.0`；
- `package.json` 与 `package-lock.json` 根包的 `engines.node` 保持完全一致；
- Node 当前最低版本口径为 `>=22.19.0`；
- `package.sh` 的打包成员明确包含 `package.json` 和 `package-lock.json`，用于首次部署时执行可复现的 npm install；
- engines 一致性由 `tests/test_version_single_source.py` 契约测试约束。

## 4. 关键行为验收

### 4.1 授权安全

- 非成员不能创建目标 workspace 授权；
- 已归档 workspace 不能创建授权；
- active 成员可以创建有效授权；
- 成员被移除后，旧授权不能继续用于 RAG；
- workspace 归档后，旧授权不能继续用于 RAG。

### 4.2 前端配置安全

- 授权等关键数据加载失败时不显示可用的保存动作；
- Profile 中存在未展示工具时，用户修改可见工具后未知工具仍被保留；
- 清空 System Policy 时，请求载荷明确包含 `system_policy: ""`；
- 辅助列表失败有独立错误状态，不误导为“暂无记录”。

### 4.3 依赖与部署

- 根 Python 依赖包含 `openpyxl`；
- Node engines 在 package 与 lockfile 中一致；
- `package.sh` 打包成员包含 package 与 lockfile；
- JavaScript 语法检查通过；
- Git diff 无空白格式错误。
