# 项目 Skill 审查与业务漏洞分析

> 文档日期：2026-08-11  
> 审查范围：项目内置 Skill、SkillRunner 线上编排、Prompt、JSON Schema、独立脚本、管理配置与报告链路  
> 审查性质：只读检查，未修改业务代码  
> 项目目录：`prd-draft-review-workflow-v1`

## 一、执行摘要

本项目共有 **6 个唯一 Skill**：

1. `docx-to-markdown`
2. `prd-overview-classify`
3. `prd-per-analysis`
4. `system-review`
5. `requirement-insights`
6. `report-generator`

草稿模式在前端配置中展示 7 个 Skill 执行位置，是因为 `report-generator` 同时承担“PRD 草稿生成”和“最终报告生成”，并不代表项目存在第 7 个 Skill。

本次检查确认：项目的基础测试覆盖和代码完整性较好，Skill 相关定向测试以及全量测试均通过；但现有测试主要验证文件存在、语法、基本 Schema 修复、调用顺序和接口契约，没有充分覆盖需求缺口识别、跨版本问题数据守恒、评审失败状态传播、管理员禁用语义等核心业务约束。

综合审查结果如下：

| 级别 | 数量 | 说明 |
|---|---:|---|
| 严重 | 2 | 会让核心分析结果为空、错误或在失败时仍显示完成 |
| 高风险 | 6 | 会导致演进追踪、评分、分类、Skill 治理或文档转换结果不可信 |
| 中低风险 | 若干 | 功能参数无效、文档与实现不一致、报告渲染和可移植性问题 |

当前不建议直接把“需求洞察与缺口分析”和“七维评审任务完成状态”作为无需人工复核的业务结论。应优先修复洞察数据链路、失败传播和 Schema 业务约束，再处理其他 Skill 的准确性与安全性问题。

## 二、审查方法与验证范围

本次审查覆盖以下内容：

- 6 个 `SKILL.md` 的能力声明、输入输出、命令示例和依赖说明。
- 各 Skill 下的 Python 脚本、Prompt、JSON Schema、模板和使用指南。
- `SkillRunner` 的线上实际调用顺序、输入组装、结果存储、错误重试和 Schema 修复。
- 审查路由中的分类、版本链、逐篇分析、七维评审、洞察、草稿和报告生成流程。
- Skill 管理后台中的启用/禁用配置与实际运行逻辑是否一致。
- DOCX、Markdown、PDF 和 Mermaid 等输入输出路径的安全性与健壮性。
- 现有 Skill 定向测试和全量项目测试。
- Ruff 静态检查和 Bandit 安全扫描。
- 针对关键疑点编写只读最小复现，不修改仓库文件。

验证结果：

```text
Skill 定向测试：52 passed
全量项目测试：1151 passed, 6 warnings
Ruff：13 个代码质量问题
Bandit：21 个提示，其中主要有效风险为 XML/压缩资源限制不足
```

6 条 Pytest warning 来自普通同步测试被错误标记为 `pytest.mark.asyncio`，与本次 Skill 核心问题无直接关系。

## 三、严重问题

### 3.1 线上需求缺口分析拿不到覆盖矩阵

**涉及 Skill：** `requirement-insights`  
**涉及线上组件：** `SkillRunner`  
**风险等级：** 严重

#### 问题描述

线上洞察流程分为三个子步骤：

1. `evolution-match`
2. `feature-extraction`
3. `gap-assessment`

`feature-extraction.md` 只要求模型输出：

```json
{
  "feature_dimensions": [
    {
      "name": "功能维度名称",
      "description": "功能描述",
      "source_doc_ids": ["doc1"],
      "category": "所属产品模块"
    }
  ]
}
```

但 `SkillRunner._build_insight_inputs()` 在进入 `gap-assessment` 时读取的是：

```python
features_result.get("coverage_matrix", [])
features_result.get("gaps", [])
features_result.get("overlaps", [])
```

由于前一步并未要求、也没有代码负责生成这些字段，因此实际传给缺口评估的三个数组通常全部为空。

#### 最小复现

向运行时传入一个符合 Prompt 的功能提取结果：

```json
{
  "feature_dimensions": [
    {"name": "功能A"}
  ]
}
```

实际构建出的缺口评估输入为：

```text
coverage_matrix = []
gaps = []
overlaps = []
```

#### 进一步的业务漏洞

独立脚本 `insights.py` 会从现有文档的 `boundary_in` 中提取功能维度，再检查这些维度是否被现有文档覆盖。由于能力全集本身来自已覆盖内容，这套算法天然难以发现“所有现有文档都没提到”的真实缺口。

要识别缺口，必须存在一个独立于现有需求文档的目标全集，例如：

- 用户自定义目标能力清单；
- 产品能力地图；
- 行业模板或领域基线；
- 上一版本规划中的目标范围；
- 由人工确认的功能维度集合。

如果没有独立基线，只能分析现有需求之间的覆盖和重叠，不能严谨地声称识别了产品缺口。

#### 业务影响

- “挖掘下一阶段需求”可能输出空缺口或泛化建议。
- 最终报告可能错误地显示需求覆盖完整。
- 用户会把没有参考基线的模型推测当成正式产品规划依据。
- 下游 PRD 草稿可能缺少真正需要补齐的能力。

#### 修复建议

1. 将 `feature-extraction` 输出扩展为标准化功能维度及其来源关系。
2. 在确定性代码中构建覆盖矩阵，不依赖模型同时生成维度和覆盖结论。
3. 为缺口分析增加必选的目标能力基线来源；没有基线时明确输出“仅完成现有需求覆盖分析，无法判断绝对缺口”。
4. 为覆盖关系增加语义匹配步骤和人工确认状态。
5. 增加端到端测试，确保 `gap-assessment` 收到非空覆盖矩阵，并验证已知缺口可以稳定检出。

### 3.2 七维评审全部失败时任务仍可能显示完成

**涉及 Skill：** `system-review`  
**涉及线上组件：** `SkillRunner`、审查任务路由  
**风险等级：** 严重

#### 问题描述

`SkillRunner._run_system_review()` 顺序执行七个维度，但不会检查维度结果是否为：

```json
{"error": "dimension ... failed"}
```

即使全部维度失败，它仍会：

- 把 7 个错误对象保存到 `review_dimensions`；
- 返回 `False`，表示“没有被取消”；
- 让上层流程继续持久化结果；
- 让审查任务把该步骤标记为完成。

#### 最小复现

模拟每个维度都返回 `{"error": "boom"}` 后，结果如下：

```text
函数返回：False
review_dimensions 数量：7
business-value：{"error": "boom"}
```

上层无法区分“七维评审成功完成”和“七个维度全部执行失败”。

#### 业务影响

- 用户看到任务完成，但报告可能为空、残缺或仅包含错误对象。
- 失败结果可能进入缓存，后续任务继续复用错误数据。
- 质量统计、任务成功率和运营指标被污染。
- 报告生成和 PRD 草稿继续基于不完整分析执行。

#### 修复建议

1. `_run_system_review()` 返回结构化执行摘要，包括成功、失败、跳过的维度。
2. 必需维度失败时抛出异常或返回明确的失败状态。
3. 允许部分成功时，任务状态必须为 `completed_with_warnings`，并记录失败维度。
4. 禁止缓存全失败或低于完整性阈值的评审结果。
5. `dimensions_executed` 只记录实际成功的维度，另设 `dimensions_failed`。
6. 为“单维失败、部分失败、全部失败、重试后成功”增加端到端测试。

## 四、高风险问题

### 4.1 跨版本演进追踪缺少后续文档内容，并会静默丢失问题

**涉及 Skill：** `requirement-insights`、`prd-per-analysis`  
**风险等级：** 高

#### 线上链路缺少证据

线上 `evolution-match` 输入包含：

- 所有逐篇分析中的边界外问题；
- 分类结果中的版本链元数据。

版本链只包含文档 ID、版本、标题等信息，没有后续版本的：

- `core_problem`；
- `boundary_in`；
- `boundary_out`；
- `key_points`；
- 原文摘录；
- 验收标准或解决方案证据。

Prompt 却要求模型判断问题是否被后续版本解决，并输出原文证据。当前输入不足以支持这一判断。

#### 独立脚本存在数据守恒错误

`insights.py` 只遍历模型返回的 `matches`。如果模型漏返回原始问题，代码不会把它补为 `unresolved`，而是让它从以下内容同时消失：

- `total_issues`；
- `resolved`；
- `partial`；
- `unresolved`；
- `boundary_issues_remaining`。

最小复现中，输入存在一个边界问题，模型返回空 `matches` 后，统计结果变成：

```json
{
  "total_issues": 0,
  "resolved": 0,
  "partial": 0,
  "unresolved": 0
}
```

#### 修复建议

1. 按版本链和当前问题所属文档构建真正的“后续文档集合”。
2. 注入后续版本的结构化分析和必要原文摘录。
3. 以原始问题列表为主表，模型结果只能更新状态，不能决定问题是否存在。
4. 模型漏返回的问题必须默认保持 `unresolved`，并标记低置信度或需人工确认。
5. 通过 `issue_id` 而不是自然语言或数组下标关联问题。
6. 验证统计守恒：`total_issues == resolved + partial + unresolved`。

### 4.2 JSON Schema 校验没有执行关键业务约束

**涉及 Skill：** 4 个 LLM Skill 以及报告输出  
**风险等级：** 高

#### 问题描述

当前 `SkillSchemaLoader` 只检查：

- 必填字段是否存在；
- 值是否属于基本 JSON 类型；
- 数组和对象的嵌套类型。

没有执行 JSON Schema 中已经声明的：

- `enum`；
- `minimum`；
- `maximum`；
- `minItems`；
- `$ref`；
- `additionalProperties`；
- 其他组合约束。

#### 最小复现

以下逐篇分析结果不会产生任何 Schema 错误：

```json
{
  "doc_id": "1",
  "core_problem": "示例",
  "category": "示例",
  "boundary_in": [],
  "boundary_out": [],
  "boundary_issues": [],
  "key_points": {"type": "nonsense"},
  "expert_review": {"summary": "示例", "checks": []},
  "quality_score": 99,
  "confidence": -3
}
```

这意味着：

- 质量评分可超出 1—5；
- 置信度可超出 0—1；
- 严重度、解决状态、文档类型可以是任意字符串；
- 专家检查项数量不足仍可能通过基础 Schema；
- `$ref` 定义的评分结构没有被完整验证。

虽然逐篇分析额外检查了 6 个 `rule_key` 是否出现，但仍未检查重复项、非法状态、空证据、空建议和分数范围。

#### 业务影响

- 质量统计和 PM 评分失真。
- 前端状态颜色和报告图标可能无法识别非法状态。
- LLM 的格式错误被静默修补为空值后仍按成功继续执行。
- 下游模型会基于错误数据继续推理。

#### 修复建议

1. 使用标准 `jsonschema` 或 Pydantic 模型完成完整校验。
2. Schema 修复后如果关键业务字段为空，不应标记为成功。
3. 区分“格式可修复”和“业务语义不可修复”。
4. 增加评分范围、枚举、最少项数、唯一性和引用解析测试。
5. 对被修复的数据保存明确的 `schema_valid=false` 和质量告警，不进入高可信缓存。

### 4.3 后台 Skill 禁用开关不影响实际执行

**涉及组件：** Skill 管理后台、`SkillConfigRepository`、`SkillRunner`  
**风险等级：** 高

#### 问题描述

后台支持把 Skill 状态设置为 `active` 或 `inactive`。仓储层列表接口会过滤禁用 Skill，但实际审查管线使用硬编码的 Skill 和步骤列表，没有在启动任务或执行步骤前检查 `SkillConfig.status`。

因此可能出现：

```text
后台状态：inactive
实际任务：仍然执行该 Skill
```

#### 业务影响

- 管理员无法真正停用出现故障、成本过高或存在风险的 Skill。
- 治理页面显示的系统状态与真实运行状态不一致。
- 紧急止损开关失效。
- 禁用后仍可能产生 LLM 调用和费用。

#### 修复建议

1. 创建审查任务前计算启用 Skill 集合。
2. 必需 Skill 被禁用时拒绝启动并说明原因。
3. 可选 Skill 被禁用时降级模式并在任务详情中展示。
4. 任务执行过程中再次检查被冻结的 Skill 配置快照。
5. 增加“禁用后不调用”“重新启用后恢复调用”的集成测试。

### 4.4 分类、版本链和依赖关系没有形成完整业务闭环

**涉及 Skill：** `prd-overview-classify`  
**风险等级：** 高

#### 已确认问题

1. 独立脚本的 `build_version_chains(..., use_llm=True)` 没有实际使用 `use_llm`。
2. `version-chain.md` 虽声明同一演进链必须属于同一分类，但脚本按 `subcategory_name` 聚类时不检查分类。
3. 最小复现已确认：分类 A 和分类 B 的文档，只要子主题同名，就能被合并到同一版本链。
4. 线上版本链 Prompt 和 Prompt 级 Schema 都没有要求输出依赖关系。
5. 路由读取 `version_chain_result.data.get("dependencies", [])`，因此依赖关系通常为空。
6. 独立脚本只生成相邻版本的 `version_successor`，没有实现 Skill 文档宣称的跨文档引用、复用、补充、兼容和解决关系识别。
7. `--version-pattern` 可能被分类配置文件中的 `version_pattern` 覆盖，命令行参数不一定真正生效。
8. 分类结果未强制限定在配置类别中，模型可能返回任意类别、`待确认` 或其他非标准值。

#### 业务影响

- 不相关需求被串成错误演进链。
- 下游架构评审拿不到真实依赖关系。
- 演进追踪基于错误链路继续判断解决状态。
- 自定义版本规则看似生效，实际仍使用默认规则。

#### 修复建议

1. 版本链的确定性约束至少包含分类、主题、版本顺序三项。
2. 使用 LLM 时只做候选链验证，不允许绕过确定性约束。
3. 将依赖识别拆为单独 Prompt 和 Schema，并保存证据片段。
4. 明确命令行参数、配置文件和默认值的优先级。
5. 对 LLM 分类结果进行类别白名单校验，低置信度进入人工确认。
6. 增加跨分类同名子主题、版本号相同、版本回退、独立版本等测试。

### 4.5 逐篇分析的独立运行模式无法可靠完成解决追踪

**涉及 Skill：** `prd-per-analysis`  
**风险等级：** 高

#### 问题一：所谓摘要只有元数据

`batch_analyze.py` 构建的 `other_docs_excerpts` 实际只包含：

```json
{
  "doc_id": "...",
  "version": "...",
  "title": "..."
}
```

没有正文摘要、核心问题、边界、关键方案或验收标准，无法用于判断一个边界外问题是否被后续版本解决。

#### 问题二：独立脚本没有正确注入 doc_id

`per-doc-analysis.md` 包含 `{{doc_id}}`，并要求模型原样返回该 ID；但 `analyze.py` 将整份 Prompt 作为 system prompt 读取，没有替换其中的占位符，同时用户消息也没有加入 `doc_id`。

脚本后续使用：

```python
raw_result.setdefault("doc_id", args.doc_id or md_path.stem)
```

如果模型已经自行生成了错误 `doc_id`，`setdefault()` 不会覆盖它。

#### 问题三：增量能力文档与脚本不一致

`SKILL.md` 声称批处理支持增量分析，但独立 `batch_analyze.py` 没有检查输出是否已存在、输入是否变化或缓存是否有效，每次都会重新分析全部文档。

#### 修复建议

1. 把 `doc_id` 作为显式参数传入 LLM 用户消息并在输出后强制覆盖。
2. 上下文必须包含后续文档的结构化分析或受控原文摘要。
3. 增量分析使用内容哈希、Prompt 版本、模型版本和 Review Context 版本组成缓存键。
4. 缓存命中必须校验输出完整性和 Schema 版本。

### 4.6 DOCX 转换存在文件覆盖冲突与资源耗尽风险

**涉及 Skill：** `docx-to-markdown`  
**风险等级：** 高

#### 文件名清洗碰撞

不同文件名可能映射到同一输出目录。例如：

```text
A:B.docx -> A_B/
A?B.docx -> A_B/
```

当前短文件名发生清洗后不会附加原始文件名哈希：

- 普通模式下，第二份文件会因目标目录已存在而被跳过；
- `--force` 模式下，第二份文件可能删除并覆盖第一份文件的输出。

#### 部分失败被永久跳过

批处理只检查目标目录是否存在，不检查 Markdown 文件、资源目录、完成标记或源文件哈希。如果上次转换创建目录后中途失败，下次不加 `--force` 会直接跳过。

#### 不可信 DOCX 资源限制不足

代码多次直接读取和解析 DOCX ZIP 中的 XML、图片和嵌入 Excel，没有看到以下限制：

- 压缩包总解压大小；
- 单个 ZIP entry 解压大小；
- 压缩比；
- XML 节点或文本大小；
- 图片数量和图片像素；
- 嵌入 Excel 文件大小和工作表规模；
- 单文档执行超时。

Bandit 对多处 `xml.etree.ElementTree.fromstring()` 给出了中高置信度风险提示。主要现实风险是异常或恶意文档造成内存、CPU 或磁盘资源耗尽。

#### 修复建议

1. 所有清洗后的名称都附加稳定的短哈希，或以文档数据库 ID 作为顶层目录。
2. 仅当存在 Markdown、完成标记且源文件哈希一致时才允许跳过。
3. 转换失败时清理临时目录，采用“临时目录转换成功后原子移动”的策略。
4. 对 ZIP、XML、图片和嵌入工作簿设置明确的资源上限。
5. 使用安全 XML 解析库，并对转换任务设置进程级超时与内存限制。
6. 增加文件名碰撞、半成品目录、ZIP bomb、大图片和超大 Excel 测试。

## 五、中低风险问题

### 5.1 `system-review --enable-vision` 参数没有实际效果

独立 `review.py` 接收 `--enable-vision`，但没有读取图片或调用视觉模型，只在元数据中记录 `vision_model`。这会让用户误以为七维评审已经理解原始文档图片。

建议删除无效参数，或真正接入逐篇分析产生的 `image_insights`，并在报告中标注图像证据来源。

### 5.2 竞品结论缺少可核验来源

`competition.md` 允许基于“行业常识”分析竞品，同时要求不要臆测。但模型常识可能过期，也可能把未知事实补齐。如果没有用户提供的竞品资料或受控行业模板，输出仍可能出现具体玩家、能力和技术路线结论。

建议：

- 将结论分为“输入证据”“行业模板”“模型推断”三种来源；
- 没有竞品材料时只输出分析框架和待调研问题；
- 对推断项设置低置信度，禁止写成确定事实；
- 如未来接入联网调研，强制保留来源、日期和引用链接。

### 5.3 报告生成参数与实现不一致

`report-generator` 存在以下问题：

- `--sections` 参数已经声明并写入使用指南，但代码从未使用它；
- `--format pdf` 仍然固定生成 Markdown 文件；
- `total_reports` 实际统计的是文件数量，MD 和 PDF 会被重复计算；
- `report-generator/requirements.txt` 没有声明 `--polish` 使用的 `anthropic`；
- 独立 PDF 渲染器固定使用 `Helvetica`，不符合“中文字体支持”的文档说明；
- 报告中的表格内容没有转义竖线和换行，可能破坏表格；
- Mermaid 标题和边标签未转义引号、方括号和特殊字符，可能生成无效图表；
- `mermaid_builder.py` 提供多种图表，但主生成流程只收集已有的演进 Mermaid，没有真正使用依赖图和时间线构建能力。

### 5.4 分类输入使用文件名兼容 doc_id，可能发生重复文件名误匹配

线上分类输入没有显式包含数据库 `doc_id`，模型通常以文件名作为标识。路由回填分类时接受“ID 相同或文件名相同”。如果同一项目存在重名文件，可能把同一分类结果匹配到多篇文档。

建议所有 Prompt 输入统一使用不可变的 `doc_id`，文件名仅作为展示字段。

### 5.5 LLM 返回格式错误后被修补为空值并继续执行

`run_skill()` 在 Schema 校验失败时会自动补齐缺失字段，但通常仍把结果标记为成功。对于分类、评分、边界和评审结果，空数组或 0 分并不一定是合法业务结果。

建议按字段划分：

- 可安全默认：可选说明、展示字段；
- 不可安全默认：分类结果、doc_id、质量评分、版本链、行动计划、问题状态。

不可安全默认字段缺失时应触发重试或失败。

### 5.6 命令示例使用 `python`，macOS 环境可能只有 `python3`

本次环境中执行文档示例的 `python` 命令失败，实际可用的是 `python3`。建议统一使用：

```bash
python3 scripts/xxx.py
```

或说明应先激活虚拟环境，并在虚拟环境中提供 `python`。

### 5.7 代码质量问题

Ruff 检出 13 个问题，主要包括：

- 未使用导入；
- 未使用局部变量；
- 无占位符的 f-string；
- 动态修改 `sys.path` 后导入导致的 E402。

这些问题不会直接造成核心业务错误，但会降低可维护性，也可能掩盖真正未完成的逻辑，例如 `doc_version`、`prefix` 等变量声明后未参与业务处理。

## 七、现有测试为什么没有发现这些问题

现有 Skill 回归测试主要覆盖：

- Skill 目录和 `SKILL.md` 是否存在；
- 文档中是否出现 `name`、`description` 字符串；
- Python 文件能否通过语法编译；
- Prompt 级 Schema 文件是否存在；
- Schema 是否能递归检查基本类型和必填字段；
- SkillRunner 是否按预期顺序调用模拟函数；
- 专家意见块是否包含 6 个规则键；
- 管理后台能否展示和切换 Skill 状态。

缺少的关键测试包括：

1. Skill 禁用后是否真的阻止执行。
2. 七维全部失败后任务是否标记失败。
3. 需求洞察是否真正构建非空覆盖矩阵。
4. 已知缺口能否稳定检出。
5. 演进问题数量是否守恒。
6. 版本链是否禁止跨分类误合并。
7. 依赖关系是否能从明确引用中被识别。
8. 非法枚举和越界评分是否被拒绝。
9. 同名或清洗后同名 DOCX 是否安全隔离。
10. 大文件、异常压缩包和半成品目录是否正确失败和恢复。
11. `--sections`、`--enable-vision` 等公开参数是否真的改变行为。
12. 中文 PDF 是否可以正确提取和显示中文文本。

因此，“1151 个测试全部通过”说明现有实现没有破坏既有契约，但不能证明 Skill 的业务推理链已经正确闭环。

## 八、建议修复路线

### 阶段一：阻止错误成功和错误结论

优先级：P0

- 修复七维评审和洞察步骤的失败传播。
- 增加 `partial`、`failed`、`completed_with_warnings` 状态。
- 禁止全失败或 Schema 关键字段为空的结果进入缓存。
- 让 Skill `inactive` 状态真正控制管线执行。
- 替换或增强 Schema 校验器，执行完整业务约束。

验收标准：

- 七维全部失败时任务必须失败。
- 任一核心步骤失败时最终报告明确标注缺失内容。
- 禁用 Skill 后不再发生对应 LLM 调用。
- 越界评分和非法状态无法进入数据库。

### 阶段二：重构需求洞察的数据模型

优先级：P0/P1

- 明确“现有需求覆盖分析”和“目标能力缺口分析”的区别。
- 引入目标能力基线。
- 确定性构建覆盖矩阵。
- 使用稳定的 `feature_id`、`issue_id` 和 `doc_id`。
- 跨版本追踪注入后续文档的结构化内容和证据。
- 确保问题状态统计守恒。

验收标准：

- 使用人工构造的能力基线，可以稳定识别已知缺口。
- 没有基线时，系统不得声称识别了绝对产品缺口。
- 模型漏返回问题时，该问题仍保留为未解决。

### 阶段三：修复分类和逐篇分析闭环

优先级：P1

- 统一所有 Prompt 的不可变文档 ID。
- 增加类别白名单和低置信度人工确认。
- 版本链增加分类一致性、主题一致性和版本顺序校验。
- 独立实现带证据的文档依赖识别。
- 修复独立逐篇分析的 doc_id、上下文和增量缓存。

### 阶段四：加固文档转换和报告交付

优先级：P1/P2

- DOCX 输出目录改用文档 ID 或稳定哈希。
- 增加 ZIP/XML/图片/Excel 资源限制和超时。
- 转换采用临时目录和原子提交。
- 实现或删除无效 CLI 参数。
- 统一 PDF 中文字体处理。
- 对 Markdown 表格和 Mermaid 内容进行安全转义。
- 修正文档、依赖文件和统计字段口径。

## 九、建议新增的自动化测试清单

### `docx-to-markdown`

- 两个清洗后同名文件不会互相覆盖。
- 转换中途失败后，下次执行不会误判完成。
- 源文件变化后缓存失效。
- 超大 ZIP entry 被拒绝。
- 超大图片和嵌入 Excel 被拒绝或降级。
- 中文 Markdown 转 PDF 后可提取中文文本。

### `prd-overview-classify`

- 跨分类同名子主题不会进入同一版本链。
- 命令行 `--version-pattern` 优先级明确。
- 模型返回未知类别时进入待确认而非直接生效。
- 明确依赖描述可以生成带证据的依赖关系。
- 重名文件使用 doc_id 正确回填。

### `prd-per-analysis`

- `doc_id` 始终与输入一致。
- `quality_score` 和 `confidence` 越界时失败。
- 专家规则缺失、重复或状态非法时失败。
- 后续文档上下文包含正文证据。
- 缓存键覆盖内容、模型、Prompt 和 Review Context 版本。

### `system-review`

- 单维失败产生部分成功状态。
- 全维失败导致任务失败。
- 错误结果不能写入可复用缓存。
- `--enable-vision` 要么执行图片分析，要么参数不存在。
- 无竞品资料时不生成未经证实的具体竞品事实。

### `requirement-insights`

- 功能提取后能生成非空覆盖矩阵。
- 给定目标能力基线时识别已知缺口。
- 无目标基线时输出能力限制说明。
- 原始问题数与状态汇总保持守恒。
- 模型漏项时问题默认保留为未解决。
- 重叠可以区分版本演进和并行冗余。

### `report-generator`

- `--sections` 真正控制章节。
- `--format md/pdf/all` 输出文件与统计一致。
- 中文 PDF 内容可读。
- Markdown 表格特殊字符正确转义。
- Mermaid 特殊字符不会破坏语法。
- 缺少可选输入时报告明确标注，而不是生成误导性完整报告。

## 十一、最终结论

项目已经具备较完整的 Skill 目录结构、Prompt 模板、结构化输出、重试机制、任务编排和测试基础。当前主要问题不是“Skill 不存在或无法运行”，而是若干关键业务链路只完成了形式上的步骤连接，没有建立可验证的数据闭环。

其中最需要立即处理的是：

1. 需求缺口分析缺少覆盖矩阵和独立目标基线；
2. 七维评审失败不会正确传播；
3. Schema 没有执行评分、枚举和最少项数等业务约束；
4. 演进问题会因模型漏返回而静默消失；
5. Skill 禁用开关没有实际运行效果。

完成上述修复后，再补齐分类依赖、逐篇分析上下文、DOCX 安全和报告参数，才能把整套 Skill 从“能够运行的分析流水线”提升为“结果可信、失败可见、可治理、可审计的需求评审系统”。
