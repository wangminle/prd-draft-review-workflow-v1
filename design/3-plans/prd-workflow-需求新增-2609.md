# PRD Workflow 需求新增计划（202609）— 管理员协助重置密码

> **当前状态（2026-08-31）**：**待评审、待排期**。本文件定义“用户发起忘记密码申请 → 管理员收到站内通知 → 线下核验身份 → 系统生成一次性临时密码并复制 → 用户登录后强制修改密码”的完整闭环。
>
> **方案定位**：面向内部部署场景，站内通知仅作为**提醒管理员处理申请**的渠道；临时密码由管理员通过已经核验可信的外部沟通工具发送给用户。本期不接入短信、邮箱或第三方身份认证服务。
>
> **核心安全原则**：系统和管理员均不能查看用户原密码；临时密码仅展示一次、限时且限用；重置后原密码和旧登录会话失效；用户设置新密码前不能进入业务页面。
>
> **范围**：§1～§4 定义需求、边界和流程；§5～§8 定义权限、数据、接口与安全契约；§9 定义前端交互；§10 为可执行 WBS；§11～§14 为验收、测试、上线与跟踪约定。

## 1. REQ-2609-001 — 管理员协助重置密码

### 1.1 背景与问题

当前系统已有以下能力：

- 用户可使用“用户名 + 密码”登录，并在登录后修改自己的密码；
- 密码使用 bcrypt 哈希存储，系统不能反向读取原密码；
- 管理员可在用户管理中手动填写新密码；
- 系统已有站内通知列表与 SSE 实时提醒；
- 当前没有登录前可发起的“忘记密码”申请，也没有临时密码、强制改密和申请处理闭环。

由此产生的问题：

1. 用户忘记密码后没有自助入口，只能线下临时联系管理员；
2. 管理员无法在系统内记录申请、核验和处理结果；
3. 现有“管理员填写新密码”容易让管理员知道用户的长期密码；
4. 如果只替换密码但不使旧会话失效，已经泄露的登录令牌仍可能继续使用；
5. 如果没有强制改密门禁，临时密码可能被长期当作正式密码使用。

### 1.2 产品目标

1. 给未登录用户提供明确、可用的密码重置申请入口；
2. 复用现有站内通知，将申请实时提醒给有权限的管理员；
3. 由管理员完成线下身份核验后，系统生成不可自定义的一次性临时密码；
4. 临时密码在管理员主动批准后尽力自动复制，并提供按钮重试和手工选中复制的降级入口；
5. 用户使用临时密码登录后必须立即设置新密码；
6. 全链路具备状态、过期、频控、权限和审计能力；
7. 不引入短信、邮箱服务及其费用和运维依赖。

### 1.3 成功指标

| 指标 | 目标 |
| --- | --- |
| 有效申请可达率 | 有效用户提交后，至少一名有效管理员可在通知中心看到申请 |
| 处理闭环率 | 已批准申请均可追踪至“用户已修改密码”或“已过期” |
| 强制改密绕过 | 0；临时密码登录后无法访问普通业务接口 |
| 敏感信息泄露 | 日志、数据库申请表、站内通知正文中均不出现临时密码明文 |
| 重复申请噪音 | 同一账号在有效待处理申请存在时不重复创建新申请和新通知 |

## 2. 范围与非目标

### 2.1 本期范围（MVP）

1. 登录页增加“忘记密码”入口；
2. 未登录用户使用用户名提交密码重置申请；
3. 系统以统一文案响应，不暴露用户名是否存在；
4. 为有效申请创建处理记录，并通知具备重置权限的管理员；
5. 管理员从通知深链进入申请详情页；
6. 管理员可批准、拒绝申请；
7. 批准时系统生成临时密码，页面仅展示一次并尝试复制；
8. 管理员通过企业微信、飞书、钉钉、电话或当面等外部渠道交付；
9. 用户以临时密码登录后进入强制改密页；
10. 新密码设置成功后临时密码失效，申请进入完成态；
11. 重置和改密均使旧 JWT 会话失效；
12. 管理端提供申请列表、筛选、状态和审计信息。

### 2.2 明确不做（本期）

- 不接入短信验证码、邮件重置链接；
- 不接入 LDAP、OIDC、企业微信、飞书、钉钉或其他 SSO；
- 不允许用户通过安全问题、身份证号等弱信息自行找回；
- 不通过站内通知向忘记密码的用户发送临时密码；
- 不允许管理员查看用户原密码；
- 不允许管理员自定义临时密码；
- 不允许多个临时密码并存；
- 不为任何管理员账号开放本功能的线上重置权限；
- 不在审计日志、应用日志、数据库申请记录中保存临时密码明文。

## 3. 角色、权限与职责

| 角色 | 能力 | 限制 |
| --- | --- | --- |
| 未登录用户 | 提交重置申请 | 不能查询账号是否存在、申请详情或处理进度 |
| 普通用户 | 使用临时密码登录、设置自己的新密码 | 强制改密完成前不能进入业务页面 |
| 管理员 | 查看普通用户申请、批准、拒绝、重新生成临时密码 | 必须先线下核验；不能查看原密码；不能通过本功能重置任何管理员账号 |
| 系统所有者 | 通过本功能以外的受控运维流程恢复管理员账号 | 本期不为管理员账号提供线上密码重置申请或批准能力 |
| 系统 | 去重、通知、生成临时密码、过期、强制改密、会话失效、审计 | 不向未登录请求方泄露用户存在性 |

### 3.1 权限默认值

- 建议新增细粒度权限 `user.password_reset.manage`；首版可映射到现有 `admin` 角色。
- MVP 的目标账号授权矩阵固定为：`admin → role=user` 允许，`admin → role=admin` 拒绝，`admin → 自己` 拒绝；批准接口必须在事务内重新读取目标用户并复核角色和状态，不能只相信申请时快照。
- 被禁用、已删除账号提交申请时，对外仍返回统一成功文案，但不创建可处理申请。
- 系统中必须始终保留至少一个可用的受保护管理员恢复路径，避免全部管理员同时无法登录。

## 4. 端到端业务流程

### 4.1 主流程

```text
用户在登录页点击“忘记密码”
  → 输入用户名并提交
  → 页面统一提示“申请已提交，请联系管理员”
  → 系统为有效账号创建待处理申请
  → 系统向有权限管理员发送站内通知
  → 管理员点击通知进入申请详情
  → 管理员通过可信的外部渠道核验用户身份
  → 管理员点击“批准并重置密码”
  → 系统使原密码、旧临时密码和旧会话失效
  → 系统生成临时密码，仅在本次响应中返回
  → 页面展示一次并尝试写入剪贴板
  → 管理员通过外部沟通工具发送给用户
  → 用户使用临时密码登录
  → 系统强制进入“设置新密码”页面
  → 用户设置新密码
  → 临时密码失效，旧会话再次失效，申请标记为已完成
  → 用户使用新密码重新登录或获得新正式会话
```

### 4.2 申请状态机

| 状态 | 含义 | 可进入方式 | 可执行动作 |
| --- | --- | --- | --- |
| `pending` | 待管理员处理 | 有效用户首次提交 | 批准、拒绝、系统过期 |
| `approved` | 已批准，临时密码有效（已处理但非终态） | 管理员完成重置或重新生成 | 用户临时登录、授权管理员重新生成、系统过期 |
| `rejected` | 已拒绝 | 管理员拒绝 | 无；用户可重新申请 |
| `expired` | 申请或临时密码已过期 | 定时/惰性检查 | 用户可重新申请 |
| `completed` | 用户已设置新密码 | 强制改密成功 | 无 |
| `superseded` | 被新一次重置替代 | 管理员重新生成或新流程替代 | 无 |

状态约束：

- 同一用户最多存在一条 `pending` 或 `approved` 的有效申请；除业务层幂等外，数据库必须使用部分唯一索引或等价约束兜底，禁止仅靠“先查再插”；
- `rejected`、`expired`、`completed`、`superseded` 均为终态；
- 管理员重新生成临时密码时，将旧记录置为 `superseded`，创建一条直接处于 `approved` 的新记录；新记录写入 `parent_request_id`、本次处理管理员和处理时间，不继承旧临时凭证，不重复发送“新申请”通知，只向管理员通知列表推送状态刷新；
- `approved` 是“已处理状态”而不是终态；其他管理员不能重复执行批准/拒绝，但任一仍具备重置权限的管理员在重新核验身份并二次确认后可执行“重新生成”；
- 状态迁移必须由数据库事务保证，避免重复点击产生两个有效临时密码。

### 4.3 异常与边界流程

| 场景 | 产品行为 |
| --- | --- |
| 用户名不存在 | 返回与存在账号完全相同的 202 文案；不创建申请、不发通知 |
| 账号已禁用/删除 | 返回统一文案；不创建可处理申请 |
| 同一账号已有待处理申请 | 不重复创建；不重复轰炸通知；可更新最近请求时间或保持原记录 |
| 申请在管理员处理前过期 | 详情页显示“已过期”，管理员不能批准；用户可重新申请 |
| 两名管理员同时批准 | 仅第一笔事务成功；第二人收到“申请已被处理”，可查看结果状态但不能查看临时密码 |
| 自动复制被浏览器拒绝或不受支持 | 保留可聚焦、可选中的一次性明文；显式复制按钮可重试 Clipboard API，同时提示使用键盘/系统菜单手工复制 |
| 管理员关闭一次性弹窗 | 不再查询或回显临时密码；只能重新生成，旧临时密码随即失效 |
| 临时密码过期 | 登录返回统一凭证错误或“临时密码已过期，请重新申请”，具体文案不得泄露额外账号信息 |
| 用户用正式旧密码登录 | 重置批准后失败 |
| 用户已有登录会话 | 批准后下一次请求返回 401，要求重新登录 |
| 临时登录后访问业务 URL | 后端返回专用错误码，前端跳转强制改密页 |
| 用户设置的新密码等于临时密码 | 拒绝，要求设置不同的新密码 |
| 用户设置的新密码不符合策略 | 展示具体密码策略；临时密码已经消费，但当前受限改密会话保持有效，直至会话或临时凭证总有效期到期 |
| 申请后账号被禁用、删除或角色变为管理员 | 批准时重新校验；拒绝处理并将申请过期/关闭，不生成临时密码 |

## 5. 关键产品与技术决策

| 编号 | 决策点 | 方案 |
| --- | --- | --- |
| **2609.a** | 通知渠道 | 站内通知只通知管理员，不承担临时密码交付 |
| **2609.b** | 身份核验 | 管理员通过组织内已有可信渠道线下核验；详情页提供“已完成身份核验”确认项 |
| **2609.c** | 密码称谓 | 产品统一使用“临时密码”，不用“密钥”，避免与 API Key/加密密钥混淆 |
| **2609.d** | 临时密码生成 | 由系统使用密码学安全随机源生成；管理员不能自定义 |
| **2609.e** | 展示与复制 | 批准接口仅在成功响应中返回一次明文；自动复制为尽力而为，不作为成功前提；前端同时提供显式复制重试和可选中文本的手工复制兜底 |
| **2609.f** | 有效期 | MVP 默认 30 分钟，可配置为 30 分钟～24 小时；到期即失效 |
| **2609.g** | 使用次数 | 临时密码只允许建立一次受限改密会话；不能作为长期凭证重复登录 |
| **2609.h** | 强制改密 | 临时登录只能访问本人信息、改密、退出和必要静态资源；后端必须强制，不只依赖前端跳转 |
| **2609.i** | 旧会话失效 | 用户增加认证版本号或等价字段；重置和完成改密时递增，JWT 校验必须匹配当前版本 |
| **2609.j** | 明文保存 | 临时密码只在内存和批准响应中短暂存在；数据库仅保存 bcrypt 哈希及过期元数据 |
| **2609.k** | 防枚举 | 登录前申请接口无论账号是否存在均返回相同状态码、响应体和近似时延 |
| **2609.l** | 通知对象 | 通知所有具备处理权限的有效管理员；任一管理员处理后，其他管理员看到同步后的“已处理状态” |
| **2609.m** | 重新生成 | 允许当前仍具备权限的管理员重新核验并生成；旧记录转 `superseded`，新记录直接为 `approved`，同时递增用户 `auth_version`，使旧临时密码、旧受限 JWT 和旧长连接立即失效 |
| **2609.n** | 现有手动改密 | 用户管理中的“手填新密码”改为“生成临时密码”主入口；如保留应急手填，也必须默认强制改密并记录审计 |

### 5.1 推荐默认参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 申请有效期 | 24 小时 | 超时未处理自动进入 `expired` |
| 临时密码有效期 | 30 分钟 | 从管理员批准成功时开始计时 |
| 同账号提交频率 | 5 分钟 1 次 | 已有有效申请时做幂等处理 |
| 同 IP 提交频率 | 10 分钟最多 5 次 | 超限仍使用不泄露账号信息的统一提示 |
| 临时密码长度 | 至少 16 字符 | 使用安全随机源，避开易混淆字符；不依赖弱口令策略放行 |
| 管理员列表默认筛选 | `pending` | 优先显示待处理项 |
| 敏感响应缓存 | `Cache-Control: no-store` | 防止临时密码被浏览器/代理缓存 |

## 6. 数据模型与持久化契约

### 6.1 `users` 扩展字段

| 字段 | 类型示意 | 用途 |
| --- | --- | --- |
| `must_change_password` | boolean，默认 false | 标记当前凭证是否只能用于强制改密 |
| `temporary_password_expires_at` | datetime，可空 | 临时密码过期时间 |
| `auth_version` | integer，默认 1 | JWT 会话版本；重置和完成改密时递增 |
| `password_changed_at` | datetime，可空 | 审计及运维展示，不保存密码明文 |

说明：临时密码批准后可以直接替换 `users.password_hash`，同时设置 `must_change_password=true` 和过期时间。这样原密码立即失效，不需要维护两套并存密码。

### 6.2 新增 `password_reset_requests`

| 字段 | 类型示意 | 约束与说明 |
| --- | --- | --- |
| `id` | integer / UUID | 主键 |
| `user_id` | FK users | 仅有效账号创建记录 |
| `parent_request_id` | FK self，可空 | 重新生成时指向被替代的旧申请 |
| `username_snapshot` | string | 便于审计账号更名，不作为认证依据 |
| `status` | enum/string | `pending/approved/rejected/expired/completed/superseded` |
| `requested_at` | datetime | 首次申请时间 |
| `last_requested_at` | datetime | 幂等重复提交的最近时间，可选 |
| `request_expires_at` | datetime | 待处理申请过期时间 |
| `processed_by` | FK users，可空 | 批准/拒绝的管理员 |
| `processed_at` | datetime，可空 | 管理员处理时间 |
| `temporary_expires_at` | datetime，可空 | 临时密码过期时间镜像 |
| `temporary_password_used_at` | datetime，可空 | 首次临时登录成功时原子写入；非空后禁止再次使用临时密码登录 |
| `completed_at` | datetime，可空 | 用户完成新密码设置时间 |
| `rejected_reason_code` | string，可空 | 使用枚举原因，不记录不必要的敏感自由文本 |
| `request_ip_fingerprint` | string，可空 | 使用服务端密钥做 HMAC-SHA256 后保存，供频控/审计；默认保留 30 天，不保存原始 IP 于申请表 |
| `created_at/updated_at` | datetime | 通用时间字段 |

数据库约束：

- 对 `user_id` 建立“状态属于 `pending/approved` 时唯一”的部分唯一索引；若目标数据库不支持部分索引，必须用可原子更新的开放态标识或等价唯一约束实现；
- `parent_request_id` 不得自引用，重新生成链只能向历史记录回指；
- 登录时通过当前唯一的 `approved` 申请确定临时凭证归属，受限 JWT 必须携带该 `password_reset_request_id`；
- 用户名输入沿用登录接口的同一规范化规则：首尾空白处理保持一致，不在本功能单独引入大小写折叠或别名匹配。

### 6.3 明确禁止持久化的内容

- 原密码明文；
- 临时密码明文；
- 管理员复制的剪贴板内容；
- 外部沟通工具名称、聊天记录或用户提交的敏感身份材料；
- 能够直接复原密码的可逆密文。

## 7. API 契约建议

> 路径命名可在实施时按现有 FastAPI 路由风格微调，但权限、幂等和敏感信息规则不得弱化。

| 方法 | 路径建议 | 权限 | 作用 |
| --- | --- | --- | --- |
| `POST` | `/api/auth/password-reset-requests` | 公开、强频控 | 提交申请；始终返回统一 202 |
| `GET` | `/api/admin/password-reset-requests` | 管理员 | 分页、按状态筛选申请 |
| `GET` | `/api/admin/password-reset-requests/{id}` | 管理员 | 查看申请详情，不含任何密码 |
| `POST` | `/api/admin/password-reset-requests/{id}/approve` | 管理员 | 原子重置并一次性返回临时密码 |
| `POST` | `/api/admin/password-reset-requests/{id}/reject` | 管理员 | 拒绝待处理申请 |
| `POST` | `/api/admin/password-reset-requests/{id}/regenerate` | 管理员 | 重新生成；旧临时密码立即失效 |
| `PUT` | `/api/auth/password/forced-change` | 受限改密会话 | 使用新密码完成强制改密 |

### 7.1 公开申请响应

无论用户名存在、禁用、已删除、处于频控或已有申请，前端均收到语义一致的响应：

```json
{
  "message": "如果账号符合条件，密码重置申请将提交给管理员。请通过组织内约定方式联系管理员。"
}
```

### 7.2 批准响应

批准成功后仅本次响应返回：

```json
{
  "request_id": 123,
  "status": "approved",
  "temporary_password": "一次性临时密码",
  "expires_at": "2026-09-01T10:30:00+08:00",
  "display_once": true
}
```

接口要求：

- 响应头包含 `Cache-Control: no-store`；
- 临时密码字段进入统一日志脱敏名单；
- 不允许 GET 再次获取明文；
- 并发批准必须通过行锁、条件更新或等价机制保证最多一次成功；
- 响应失败或前端丢失后不能恢复同一个明文，只能执行“重新生成”。

### 7.3 登录与强制改密响应

- 登录接口识别 `must_change_password=true` 且未过期的临时凭证；
- 临时密码校验成功时，在同一事务内将对应申请的 `temporary_password_used_at` 从空更新为当前时间；条件更新失败表示已被使用，拒绝再次签发受限会话；
- 返回受限 JWT，声明中带 `auth_version`、`password_change_required=true` 和 `password_reset_request_id`；其 `exp` 不得晚于 `temporary_expires_at`；
- `/api/auth/me` 同步返回 `must_change_password`，便于页面刷新后继续恢复强制改密页；
- 后端中间件对受限 JWT 采用精确白名单放行：`GET /api/auth/me`、`PUT /api/auth/password/forced-change`；其余受保护 API 返回 403 和稳定错误码 `PASSWORD_CHANGE_REQUIRED`，禁止仅靠前端隐藏导航；静态资源和公开健康检查不属于受限 JWT 授权范围；
- 每次使用受限 JWT 时，中间件除校验 `auth_version` 外，还必须校验 `password_reset_request_id` 指向该用户当前唯一、未过期且状态为 `approved` 的申请；重新生成、替代或过期后，旧受限 JWT 即使尚未到自身 `exp` 也必须失败；
- 强制改密成功后递增 `auth_version`，使受限 JWT 失效，再签发正式 JWT 或要求重新登录。
- 强制改密接口必须同时校验 JWT 中的 `password_reset_request_id` 仍是该用户当前唯一 `approved` 申请，避免重新生成后旧受限会话完成错误申请。

## 8. 安全、审计与并发要求

### 8.1 安全要求

1. 使用 `secrets` 或等价密码学安全随机源生成临时密码；
2. 临时密码只保存 bcrypt 哈希；
3. 本期沿用现有正式密码策略，临时密码自身至少 16 位；正式密码最小长度提升另立安全改进项，不作为本期验收前置；
4. 重置批准时递增 `auth_version`，旧 JWT 在服务端校验失败；
5. 完成强制改密时再次递增 `auth_version`；
6. 管理员批准、拒绝、重新生成均需 CSRF/同源和管理员鉴权保护；
7. 公开申请接口按账号、IP 指纹和全局速率做分层限流；
8. 管理员一次性弹窗禁止在 DOM 中长期保留临时密码，关闭后主动清空节点变量；
9. 不在 URL、查询参数、通知正文、页面标题、埋点或错误上报中携带临时密码；
10. 剪贴板由管理员负责粘贴至可信工具；页面明确提醒不要发送到群聊或工单公开评论。
11. `auth_version` 变化时，除普通 HTTP 请求校验外，还必须关闭该用户现有的通知 SSE、WebSocket 或其他长连接，或在每次推送前重新校验版本；不能让旧连接在重置后继续接收数据。
12. 网关、反向代理、APM 和错误采集系统必须同步禁止记录批准/重新生成接口的请求体与响应体。

### 8.2 审计事件

| 事件名建议 | 记录内容 | 禁止记录 |
| --- | --- | --- |
| `auth.password_reset.requested` | 请求时间、结果分类、IP 指纹、是否去重 | 用户提交的密码、完整敏感网络信息 |
| `admin.password_reset.approved` | 申请 ID、目标用户 ID、管理员 ID、过期时间 | 临时密码明文/哈希 |
| `admin.password_reset.rejected` | 申请 ID、目标用户 ID、管理员 ID、原因码 | 敏感自由文本 |
| `admin.password_reset.regenerated` | 新旧申请 ID、目标用户 ID、管理员 ID | 新旧临时密码 |
| `auth.password_reset.temp_login` | 用户 ID、申请 ID、成功/失败原因码 | 临时密码 |
| `auth.password_reset.completed` | 用户 ID、申请 ID、完成时间 | 新密码及哈希 |
| `auth.session.version_mismatch` | 用户 ID、令牌版本与当前版本 | JWT 原文 |

### 8.3 通知一致性

- 复用现有通知服务的 `defer_push` 语义：数据库事务提交成功后再推 SSE，避免产生指向回滚申请的“幽灵通知”；
- 通知 `type` 建议使用 `password_reset_request`，`target_type=password_reset_request`，`target_id=申请 ID`；
- 通知深链打开管理员的“密码重置申请详情”，不直接执行批准；
- 一名管理员处理后，其他管理员的通知点击应显示最新状态，不允许重复批准/拒绝；重新生成必须走独立动作、重新核验和二次确认；
- 通知标题不包含临时密码，建议为“用户申请重置密码”；正文仅包含用户名和申请时间等必要信息。

## 9. 前端交互设计

### 9.1 登录页：忘记密码

- 在密码输入框下方增加“忘记密码？”文本按钮；
- 点击后打开独立弹窗或登录页内步骤，不要求先登录；
- 字段仅包含“用户名”，不收集手机号、邮箱或申请理由；
- 提交成功后显示统一文案，并提示用户通过组织内约定方式联系管理员；
- 提交按钮需防重复点击，失败时区分网络故障与统一业务响应。

### 9.2 管理员通知与详情页

通知示例：

> **用户申请重置密码**  
> 用户 `zhangsan` 于 2026-09-01 10:00 提交申请。请先通过可信渠道核验本人身份，再处理该申请。

详情页展示：

- 用户名、账号状态、角色；
- 申请时间、过期时间、当前状态；
- 最近活动时间，辅助管理员判断但不能替代身份核验；
- “我已通过可信渠道核验申请人身份”确认框；
- “拒绝申请”和“批准并重置密码”按钮；
- 如果申请提交后目标账号角色已变为管理员，详情页显示“管理员账号不能通过本功能重置”，所有处理按钮禁用。

### 9.3 批准确认

管理员点击批准前显示二次确认：

> 确认后，该用户的原密码、旧临时密码和已有登录会话将失效。系统将生成一个仅展示一次的临时密码。请仅通过已核验的可信外部沟通工具发送给用户。

管理员必须勾选身份核验确认项后才能提交。

### 9.4 一次性临时密码弹窗

批准成功后：

1. 显示临时密码和失效时间；
2. 在批准响应返回后尝试调用 Clipboard API 自动复制；由于浏览器可能在异步请求后撤销用户激活，自动复制仅作为体验增强；
3. 自动复制成功时提示“临时密码已复制”；
4. 自动复制失败时提示“自动复制失败，请点击复制按钮或选中文本手工复制”；明文区域必须可聚焦、可选择，显式按钮失败时仍可使用键盘快捷键或系统菜单复制；
5. 显示交付提醒：“请通过可信外部工具单独发送给用户，不要发送到群聊”；
6. 关闭前提示：“关闭后将无法再次查看；如已丢失，只能重新生成”；
7. 关闭后前端清空明文，不提供历史查看入口。

### 9.5 用户强制改密页

- 临时密码登录成功后不进入首页，直接进入全屏“设置新密码”；
- 不显示普通导航、通知、项目数据或其他业务内容；
- 输入新密码和确认密码，不再要求输入旧临时密码；
- 明确展示密码规则；
- 新密码不得与临时密码相同；
- 修改成功后提示“密码已更新，请使用新密码重新登录”，或由系统签发正式会话后进入首页；实施默认采用**要求重新登录**，边界最清晰。

## 11. 验收标准

### 11.1 主路径验收

- 登录页存在“忘记密码”入口，未登录用户可以提交用户名；
- 有效用户提交后，管理员实时收到站内通知；
- 管理员点击通知可打开对应申请详情；
- 未勾选“已完成身份核验”时不能批准；
- 批准后系统生成临时密码，自动复制成功时有明确提示；
- Clipboard API 不可用时，临时密码文本仍可聚焦、选中并通过键盘快捷键或系统菜单手工复制；
- 临时密码弹窗关闭后不能再次查看同一个密码；
- 原密码在批准后立即不能登录；
- 用户使用临时密码登录后只能进入强制改密页；
- 设置新密码成功后，临时密码不能再次使用；
- 用户可用新密码正常登录，申请状态为 `completed`。

### 11.2 安全验收

- 存在账号与不存在账号提交申请的状态码、响应体保持一致；
- 高频提交被限制且不会造成管理员通知风暴；
- 两名管理员并发批准时最多生成一个有效结果；
- 重置批准前签发的所有 JWT 在批准后失效；
- 临时登录受限 JWT 不能访问项目、对话、评审、管理等业务接口；
- 临时密码过期后不能登录；
- 临时密码首次登录成功后即标记已消费；退出、关闭页面或丢失受限会话后不能再次使用，只能请管理员重新生成；
- 重新生成后旧临时密码和旧受限会话失效；
- 受限 JWT 的 `exp` 不得晚于临时密码失效时间；临时密码过期或申请被替代后，已经签发的受限 JWT 和长连接同步失效；
- 任一管理员都不能通过本功能重置自己或任何其他管理员账号；
- 数据库、审计日志、应用日志、站内通知、URL 和前端持久化中均不存在临时密码明文；
- 所有密码仍仅以 bcrypt 哈希形式持久化。

### 11.3 体验验收

- 申请、待处理、批准、拒绝、过期、完成状态使用一致中文文案；
- 管理员从通知到处理详情只需一次点击；
- 复制状态和失效时间清晰可见；
- 用户刷新强制改密页后仍停留在改密流程；
- 网络失败不会误提示“重置成功”，重复点击不会产生多个临时密码；
- 键盘操作、焦点顺序、表单标签和错误提示满足基本可访问性要求。

## 13. 上线、灰度与回滚

### 13.1 上线前置

1. 备份数据库并验证恢复；
2. 对存量用户补齐 `auth_version=1`、`must_change_password=false`；
3. 确认至少一名管理员能正常登录并收到通知；
4. 配置频控、申请有效期和临时密码有效期；
5. 校验生产日志脱敏规则包含 `temporary_password`；
6. 完成一次“管理员账号处理普通用户账号”的真实双账号演练，禁止将任何管理员账号作为重置目标。

### 13.2 灰度策略

- 使用功能开关控制登录页入口与公开申请 API；
- 功能开关只允许停止创建新申请；只要仍存在 `approved` 申请或 `must_change_password=true` 用户，临时登录、认证版本校验和强制改密端点必须继续运行；
- 第一阶段仅开放普通用户申请，管理员/受保护账号继续走线下运维；
- 观察申请量、重复率、平均处理时长、过期率、复制失败率和强制改密完成率；
- 稳定后再决定是否开放管理员账号的专门恢复流程。

### 13.3 回滚边界

- 关闭公开申请入口不应影响已经完成改密的用户；
- 不回滚已经递增的 `auth_version`，避免旧 JWT 重新有效；
- 不允许回滚到不校验 `auth_version` 或不执行 `must_change_password` 后端门禁的应用版本；发布工具必须把这一条件做成回滚前置检查；
- 已批准但尚未完成的用户，回滚前必须由管理员重新设置安全凭证或继续保留最小强制改密端点；
- 批准重置已覆盖原 `password_hash`，不得通过恢复旧数据库备份或旧用户行让原密码重新生效；如需恢复业务数据，必须保留当前用户凭证、`auth_version` 和重置状态；
- 数据库新增字段必须保留，不做破坏性降级；目标版本必须同时理解并强制执行这些认证字段；
- 回滚后应将未完成申请标记为 `expired` 或通过运维脚本显式收口，不能静默悬挂。
